## 0. 前置判断：这个功能推翻了两个既有前提

在写任何代码之前，必须先承认两件事。

### 0.1 架构前提被打破：从"零后端"变成"必须有云端"

当前项目是**纯本地架构**：词库打包进包内、进度存 `wx.setStorageSync`、无账号体系、无服务器、成本 ¥0。

但"圈子""好友""排行"的本质是**多用户数据交换**——A 的数据要到 B 的手机上。这在小程序里只有两条路：

| 方案 | 可行性 |
|---|---|
| 小程序直接 P2P 同步 | ❌ 小程序没有 P2P / WebSocket 到客户端的通道 |
| 自建后端服务器 | ⚠️ 可行，但要 HTTPS + ICP 备案域名，成本与运维都上来 |
| **微信云开发** | ✅ 最省事：自带 openid 身份、云数据库、云函数，无需备案域名 |

**结论：必须引入微信云开发。** 成本从 ¥0 变为 ¥19.9/月（PERSONAL，40000 资源点）或先用免费额度。
注意免费额度的坑：小程序**发布后到期时间变为上线后第 15 天**，不是无限期免费。

### 0.2 产品红线被触碰：原定"不做小学生排行榜"

项目定位文档里明确写过：**不做小学生排行榜**（隐私/体验红线）。

原因不是技术，是心理：公开排名对 6-12 岁儿童会产生比较焦虑，圈内排名靠后可能带来社交压力，甚至成为同学间的嘲笑素材。

本方案的处理方式不是"取消排行"，而是**改造排行的形态**：

| 原始需求 | 改造后 | 理由 |
|---|---|---|
| 谁背得多排名 | 不按词数排 | 直接鼓励刷量 |
| 完整名次列表 | 只显示"已完成 N/M 人" + 自己的位置 | 不制造"倒数第一" |
| 全站/全年级榜 | 仅熟人小圈子（≤20 人） | 熟人圈压力可控，公开榜不可控 |
| 默认开启 | 默认关闭，圈主主动开启"名次模式" | 把选择权交给家长/老师 |

**这三条是硬约束，不是建议。** 如果坚持要完整名次榜，需要重新评估产品风险。

### 0.3 还有一条合规风险（需你确认）

小程序的**服务类目**里，"社交"相关（社区/论坛/交友）通常要求企业主体资质，个人主体可选类目有限。

加了"好友 + 圈子 + 排行"可能被判为社交功能，导致审核被拒或上线后被下架整改。

**规避思路**（不保证一定过审）：
- 圈子不设公开广场、不支持搜索发现，**只能邀请加入**，人数上限 20
- 定位表述为"学习小组"而非"社交/交友"
- 不做陌生人推荐、不做内容发布（无 UGC 文本，只有指标数字）

**这个风险需要你先去小程序后台确认当前类目政策，再决定是否投入开发。**

## 1. 整体架构与模块划分

### 1.1 分层

```
┌──────────────────────────────────────────────┐
│ 展示层  圈子页 / 好友页 / 成员详情页 / 邀请落地页    │  新增
├──────────────────────────────────────────────┤
│ 社交层  圈子服务 / 好友服务 / 排行服务            │  新增（读云端）
├──────────────────────────────────────────────┤
│ 同步层  快照上报 / 快照拉取 / 离线队列             │  新增
├──────────────────────────────────────────────┤
│ 聚合层  从 wb_rlog 汇总出 DailySnapshot          │  新增（本地计算）
├──────────────────────────────────────────────┤
│ 学习层  srs / fsrs / dict / speech  ...         │  不变
├──────────────────────────────────────────────┤
│ 存储层  本地 Storage（权威） + 云数据库（共享副本）  │  扩展
└──────────────────────────────────────────────┘
```

### 1.2 核心设计原则：只上云聚合值，明细永不出设备

这是整个方案的基石。

- 上云的是"今天学了 12 个词、首次正确 9/12、连续 5 天"这种**数字**
- **不上云**：具体背了哪些词、错了哪些词、每题的耗时
- 理由有三：省流量与存储、降低隐私风险、缩小攻击面

一条必要的补充：老用户首次接入时，从本地 `wb_rlog_YYYY-MM` **回算近 30 天**的聚合快照补传，
否则会出现"我学了三个月，圈里显示 0 天"的尴尬。

### 1.3 模块清单

| 模块 | 位置 | 职责 |
|---|---|---|
| `services/social/snapshot.js` | 本地 | 从 rlog 汇总当日指标，写本地快照 |
| `services/social/sync.js` | 本地+云 | 节流上报、拉取、离线队列、冲突处理 |
| `services/social/circle.js` | 云调用 | 建圈/加入/退出/成员列表 |
| `services/social/friend.js` | 云调用 | 邀请、确认、删除、列表 |
| `services/social/rank.js` | 本地 | 从成员快照算榜（不存表） |
| `cloudfunctions/social/*` | 云函数 | 鉴权、写库、短码生成、反刷校验 |
| `pages/circle/*` | 页面 | 圈子列表、圈子详情、排行 |
| `pages/friend/*` | 页面 | 好友列表、好友详情、邀请 |

**必须走云函数而不是客户端直连数据库**，原因：
- 排行需要跨用户读取，客户端权限规则做不到
- 邀请码校验、人数上限、反刷逻辑必须在服务端
- 好友的双向写入需要事务性

## 2. 圈子与好友的关系

这是最容易被设计混的地方。两者是**正交**的两种关系，不是包含关系。

| 维度 | 好友 | 圈子 |
|---|---|---|
| 本质 | 人际关系 | 场景关系 |
| 基数 | 1 对 1，双向 | 1 对多，成员制 |
| 绑定教材 | 不绑定，看所有教材的汇总 | **必须绑定一本** |
| 生命周期 | 长期，需双方同意 | 有始有终，可退可散 |
| 数据可见范围 | 跨教材的长期指标 | 仅本圈教材的当日指标 |
| 能否独立存在 | 能 | 能（圈子不需要好友） |

### 关系图

```
        ┌─────────┐   邀请     ┌─────────┐
        │  好友   │ ────────→ │  圈子   │
        │ (双向)  │ ←──────── │ (多成员)│
        └─────────┘  一键加友  └─────────┘
             │                      │
             │ 可不在同一圈          │ 成员间可以只是"同圈"，不是好友
             ↓                      ↓
        跨教材长期数据          同教材当日数据
```

### 三条关键规则

1. **圈内成员不必是好友**。进圈即形成"监督关系"，比"好友"轻。避免强迫加好友。
2. **好友不必在同一圈**。好友可能学不同教材，只能看汇总进度，不能进同一排行。
3. **好友是邀请进圈的主路径**，但不是唯一路径（还支持邀请码、群分享）。

**为什么这样切**：如果圈子强制要求全员互为好友，会让"只想找几个人一起背"的场景变得很重；
如果好友自动共享教材数据，又会在用户没注意时泄露学习内容。

## 3. 关键数据模型

全部在微信云开发数据库。命名用 snake_case，与云开发控制台一致。

### 3.1 `users` — 用户档案

| 字段 | 类型 | 说明 |
|---|---|---|
| `_openid` | string | 主键，云开发自动注入 |
| `nick_name` | string | 昵称，可用 `chooseAvatar`/`type=nickname` 获取 |
| `avatar_file_id` | string | 云存储 fileID |
| `grade` | number | 1-6，用于教材推荐 |
| `active_textbook_id` | string | 当前主学教材 |
| `created_at` / `last_active_at` | number | 时间戳 |
| `settings.share_progress` | boolean | 默认 `false` |
| `settings.share_accuracy` | boolean | 默认 `false` |
| `settings.join_ranking` | boolean | 默认 `true`（但名次模式默认关） |

### 3.2 `textbook_progress` — 教材维度累计进度

| 字段 | 类型 | 说明 |
|---|---|---|
| `_openid` + `textbook_id` | string | **复合唯一** |
| `learned_count` | number | 该册已学词数 |
| `mastered_count` | number | `due` 间隔 ≥30 天的词数 |
| `total_count` | number | 该册总词数（来自 `units.json`） |
| `updated_at` | number | |

索引：`(_openid, textbook_id)` 唯一。

**为什么要单独一张表**：`learned_count` 是累计值，不是当日增量。圈子要显示"张学了 45%"，
这个比例算不出来就只能靠这张表。

### 3.3 `circles` — 圈子

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | string | |
| `name` | string | 圈名，≤12 字 |
| `textbook_id` | string | **必填，绑定一本教材** |
| `owner_openid` | string | 圈主 |
| `invite_code` | string | 6 位大写字母+数字，唯一，可重置 |
| `join_policy` | string | `invite`（仅邀请）/ `code`（凭码）/ `approval`（需审核） |
| `max_members` | number | **固定 20，不可改** |
| `member_count` | number | 冗余计数，加入/退出时增减 |
| `rank_mode` | string | `status`（默认，只显示完成状态）/ `ranked`（显式名次） |
| `status` | string | `active` / `archived` |
| `created_at` | number | |

索引：`invite_code` 唯一；`textbook_id + status`。

**`max_members = 20` 是刻意设的上限**，不是性能考虑。人数一多，圈子就退化成社区，
既撞类目风险，也违背"熟人监督"的初衷。

### 3.4 `circle_members` — 成员关系

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | string | |
| `circle_id` + `openid` | string | **复合唯一** |
| `role` | string | `owner` / `member` |
| `alias` | string | 圈内昵称，可覆盖全局昵称（同一人在不同圈可用不同称呼） |
| `joined_at` | number | |
| `status` | string | `active` / `quit` / `removed` |

索引：`(circle_id, openid)` 唯一；`(openid, status)` 查"我的圈子"。

### 3.5 `friendships` — 好友关系（双行存储）

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | string | |
| `owner_openid` | string | 归属方（"我的好友列表里"） |
| `friend_openid` | string | 对方 |
| `status` | string | `pending` / `active` / `blocked` |
| `source` | string | `share`（分享卡片）/ `circle`（同圈加友） |
| `created_at` / `accepted_at` | number | |

索引：`(owner_openid, friend_openid)` 唯一；`(owner_openid, status)`。

**为什么双行而不是单行**：单行（存 min/max 排序）省一半空间，但两个问题——
拉黑时无法区分方向（A 屏蔽了 B，B 是否还能看到 A？）；删好友时无法做"单边删除"。
双行各存各的状态，语义清晰。代价只是一次写入写两行，用云函数事务保证。

**一致性规则**：`A→B` 与 `B→A` 的 status 必须同步变更。接受邀请时两条一起改成 `active`；
A 拉黑 B 时，`A→B` = `blocked`，`B→A` 保持不变但查询时需排除"对方 blocked 我"的情况。

### 3.6 `daily_snapshots` — 每日快照（核心表）

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | string | `${openid}_${date}`，天然幂等 |
| `openid` | string | |
| `date` | string | `YYYY-MM-DD`，**按 04:00 切日** |
| `textbook_id` | string | 当天主要在学的教材 |
| `new_learned` | number | 当日新学词数 |
| `reviewed` | number | 当日复习词数 |
| `first_try_correct` | number | 首次作答正确数 |
| `first_try_total` | number | 首次作答总数 |
| `study_ms` | number | 学习时长 |
| `completed` | boolean | 当日计划是否完成 |
| `streak` | number | 截至当日的连续打卡天数（**冗余存储**） |
| `updated_at` | number | |

索引：`(openid, date)` 唯一；`(date, textbook_id)` 供圈子聚合查询。

**`streak` 为什么冗余**：不冗余就得每次从最早快照链式累加，查 20 个人的榜要读几百条。
写快照时算好存下来，读的时候一次拿完。代价是"补考/改数据"时要重算，可接受。

**`first_try_*` 的口径是这张表最关键的地方**，见 4.2。

### 3.7 不建的表

| 表 | 为什么不建 |
|---|---|
| `circle_ranks` 排行缓存 | 20 人 × 1 天 = 20 次读，实时算足够快。加缓存只会引入"缓存与真值不一致"的新问题 |
| `invites` 邀请记录表 | 邀请码直接挂在 `circles` 上，不需要单独的邀请生命周期 |
| 词条级同步表 | 违反 1.2：明细永不出设备 |

## 4. 排行与打卡规则

### 4.1 打卡判定

```
completed = (当日 new_learned >= 计划新词数) AND (当日到期复习队列已清空)
```

三个细节：

- **计划新词数**取当日生效的 `plan.dailyNewWords`。用户中途改计划，以当日 0 点时的值为准
  （否则改一下计划就能把昨天判成完成）。
- **"复习队列清空"**指 `due <= today` 的词全部处理过至少一次。不是"全部答对"。
- **不提供补卡**。SRS 的复习是按时效算的，补卡没有学习价值，且极容易变成刷指标。

**跨天切点用 04:00 而不是 00:00**，理由是真实使用场景：小学生 22:30 开始学、23:50 学完，
或者 00:10 才学完。按 00:00 切会把一次完整学习拆成两天，导致"永远差一点没完成"。
04:00 覆盖了绝大多数夜间学习。

### 4.2 正确率口径（最容易做错的地方）

```
accuracy = first_try_correct / first_try_total
```

**只统计该词当日第一次作答，重复作答不计入。**

原因在 FSRS 的实现里：一个新词当天会连出「新词卡 → 词义选择 → 中译英 → 拼写」4 道题。
如果全算，一个词贡献 4 个分母，正确率被做题数量稀释；
更糟的是用户可以靠反复重答把正确率刷上去。

实现方式：聚合时按 `(word_id, date)` 去重，只取当天第一条 `rlog` 记录。

**边界**：`first_try_total = 0`（只看了不答）时，`accuracy` 记为 `0` 而不是 `1`，
避免"什么都没做却 100% 正确"。

### 4.3 排行规则（两种模式）

#### 默认模式：`status` —— 只显示完成状态

不排名次。圈子页展示：

```
今日已完成 8 / 12 人
──────────────
✓ 小明    连续 12 天
✓ 小红    连续 9 天
✓ 我      连续 5 天
◯ 小刚    —（今天还没开始）
```

排序：已完成 → 未完成；组内按 `streak` 降序，同 streak 按 `updated_at` 升序（先完成的在前）。

**没有"第 1 名"，只有"完成了"。** 这是对 0.2 红线的直接落地。

#### 可选模式：`ranked` —— 显式名次（圈主手动开启）

```
score = 40 × done + 30 × min(streak,30)/30 + 30 × accuracy
```

| 分项 | 权重 | 理由 |
|---|---|---|
| 今日完成 | 40 | 行为的唯一硬指标，必须占大头 |
| 连续天数 | 30 | 反映坚持度，30 天封顶防止老用户永久霸榜 |
| 正确率 | 30 | 反映质量，但不能占太高，否则只答简单词的人占便宜 |

**为什么不能单一指标**：
- 只按词数 → 疯狂刷量，11 点前把整册"过"一遍
- 只按正确率 → 只答最熟的词，不学新的
- 只按 streak → 老用户永久第一，新人没有参与感

三分项组合后，任何单项作弊都会被另外两项拉下来。这是"防钻空子"的最小设计。

### 4.4 更新时机

| 事件 | 动作 | 频率 |
|---|---|---|
| 每次 `applyAnswer` 后 | 更新**本地**快照（同步写 Storage） | 每答一题 |
| 页面 `onHide` / 每日首次进入 / 下拉刷新 | **上报云端** | 节流，最少间隔 30s |
| 进入圈子页 `onShow` | 拉取成员快照算榜 | 缓存 60s |
| 跨天（本地日期变化） | 结算昨日、重置今日、检查 streak | 每日首次打开 |
| 联网恢复 | 冲刷离线队列 | 事件驱动 |

**绝不能每题上报**：一次学习 20 题就是 20 次云调用，
既烧资源点又拖慢答题响应。答题链路的性能优先于数据实时性。

### 4.5 streak 计算

```
若 昨日 completed = true  →  streak = 昨日 streak + 1
若 昨日 completed = false →  streak = 1（今天重新起算）
```

在**本地**算，随快照一起上传。不做服务端链式计算，因为客户端离线期间也要显示正确的 streak。

## 5. 微信邀请与加好友流程

### 5.1 一个必须知道的技术边界

**小程序拿不到微信好友列表。**

微信不向小程序开放关系链（open-data 里的 `getFriendCloudStorage` 只在游戏类目可用，
且只返回玩过同款游戏的微信好友）。所以"通过微信邀请加好友"的实际形态是：

> 你生成一张带参数的分享卡片 → 发给微信好友或群 → 对方**点击** → 进入小程序 → 建立小程序内好友关系

**不是**"读取通讯录然后一键添加"。任何号称能做到这点的方案都是假的。

### 5.2 邀请进圈

```
圈主/成员点击「邀请搭子」
   ↓
onShareAppMessage 生成卡片
   path = /pages/circle/join?cid=<circleId>&code=<inviteCode>
   ↓
对方在微信里点击卡片
   ↓
小程序冷启动 → join 页
   ↓
云函数 verifyInvite(cid, code)
   ├─ 圈子存在且 active？
   ├─ member_count < 20？
   ├─ 邀请码有效？
   └─ 是否已在圈内？（幂等，直接跳详情）
   ↓
写 circle_members 一行 + member_count + 1
   ↓
若对方与邀请人还不是好友 → 顺手建 friendships 双行（source='circle'）
   ↓
跳圈子详情页，展示"你已加入 X 的圈"
```

**邀请码双通道**：分享卡片走 `cid+code`（精确），口头传播走 6 位码（容错）。
6 位码用 `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`（去掉 I/O/0/1，防止读错）。
生成时需查重，冲突则重试。

### 5.3 单独加好友

```
A 在好友页点「邀请好友」
   ↓
生成 invite_token（一次性，24h 有效）
   ↓
分享卡片 path = /pages/friend/accept?t=<token>
   ↓
B 点击 → 看到「A 想加你为学习搭子」+ A 的昵称头像
   ↓
B 点「同意」
   ↓
云函数事务：写 A→B active、B→A active
   ↓
双方好友列表出现对方
```

**为什么必须双向确认**：单向加好友等于任何人都能把你加进他的列表并查看你的数据。
对未成年人产品，这是不可接受的设计。

### 5.4 隐私边界（分级表）

先明确一个容易搞反的点：**好友看的是"长期、跨教材"的数据，圈内看的是"当日、同教材"的数据**。
两者的可见字段集合不同，不是简单的包含关系。

| 字段 | 自己 | 好友 | 同圈成员 | 同圈且好友 | 陌生人 |
|---|---|---|---|---|---|
| 昵称 / 头像 | ✔ | ✔ | ✔ | ✔ | ✘ |
| 当前在学教材 | ✔ | ✔ | ✔（本圈教材） | ✔ | ✘ |
| 教材总进度 % | ✔ | ✔ | ✔ | ✔ | ✘ |
| 今日是否完成 | ✔ | ✔ | ✔ | ✔ | ✘ |
| 连续打卡天数 | ✔ | ✔ | ✔ | ✔ | ✘ |
| 正确率 | ✔ | 需开关 | 需开关 | 需开关 | ✘ |
| 学习时长 | ✔ | 需开关 | ✘ | 需开关 | ✘ |
| **具体错词** | ✔ | **永不** | **永不** | **永不** | ✘ |
| **词条级明细** | ✔ | **永不** | **永不** | **永不** | ✘ |
| 其他教材的进度 | ✔ | ✔（汇总） | **✘** | ✔ | ✘ |

三条硬规则：

1. **错词与词条明细永不外泄**。这是底线——错词暴露的是"这个孩子哪里不会"，
   对小学生来说是最敏感的信息。
2. **圈内只看本圈教材**。A 在圈 1 学 pep_3a、圈 2 学 pep_4a，两个圈的人互相看不到对方圈的数据。
3. **默认全关，主动开启**。`share_progress` / `share_accuracy` 默认 `false`。
   首次进圈子页时弹一次说明，用户点了同意才上报。

**退圈与拉黑的效果**：
- 退圈 → 停止上报，圈子页不再显示该成员；已上传的历史快照保留 30 天后清理
- 拉黑 → 立即从对方所有可见列表中消失，且对方无法再邀请你进圈

## 6. 边界情况

| # | 场景 | 处理方式 |
|---|---|---|
| 1 | **老用户首次接入** | 从本地 `wb_rlog` 回算近 30 天快照补传，否则显示"学了 0 天" |
| 2 | **离线答题** | 本地正常计分，快照进队列，联网后按 `_id` 幂等 upsert |
| 3 | **改系统时间刷打卡** | 服务端做日期校验：客户端 `date` 与服务端日期差 > 1 天则拒绝写入 |
| 4 | **客户端改 Storage 刷数据** | 只能防君子。加服务端合理性校验：单日 `new_learned` > 教材总词数则丢弃；`study_ms` 与题量比例异常则标记待审 |
| 5 | **圈子绑定的教材没人学** | 成员 `active_textbook_id` 与圈子不同 → 该成员当日不参与排行，显示"未学本册" |
| 6 | **一人多圈同学一本教材** | 快照共用一份（按 openid+date 唯一），多个圈读同一条，天然一致 |
| 7 | **圈主退出** | 转让给最早加入的 active 成员；无人可转让则圈子归档 |
| 8 | **成员满 20 还想加人** | 提示"圈子已满"，引导新建圈 |
| 9 | **好友删了又加** | `friendships` 保留历史行，status 在 `blocked`/`active` 间切换，不物理删除 |
| 10 | **同一人反复进退圈** | `circle_members` 保留历史行，`status` 变更；唯一索引建在 `(circle_id, openid)` 上需改为"仅 active 唯一"用部分索引，或改为软删后允许重复行 |
| 11 | **夜间 23:50 学到 00:10** | 04:00 切日，算同一天 |
| 12 | **两个老师建同名圈** | 圈子不公开可搜，同名无影响；圈名不做唯一约束 |
| 13 | **云开发资源点超限** | 降频上报、排行缓存 60s、快照只保留 90 天 |

第 10 条要特别说明：如果 `(circle_id, openid)` 做硬唯一，退圈后再进会撞键。
两种解法——软删 + 部分唯一索引（云开发不支持部分索引），或者保存历史行但加 `seq` 字段参与唯一键。
**本项目建议前者改为"唯一索引建在 `_id` 上，查询时按 status 过滤"，牺牲一点约束换取灵活性。**

## 7. 设计取舍汇总

| 取舍点 | 选择 | 放弃的方案 | 理由 |
|---|---|---|---|
| 后端 | 微信云开发 | 自建服务器 / 纯本地 | 无需备案、自带 openid、成本最低 |
| 同步粒度 | 每日聚合快照 | 词条级实时同步 | 隐私、流量、成本三重收益 |
| 排行形态 | 完成状态优先，名次可选 | 完整名次榜 | 小学生心理安全 |
| 圈子规模 | 上限 20 人 | 不限人数 | 防退化为社区，降低类目风险 |
| 好友关系 | 双行 + 双向确认 | 单行 / 单向关注 | 拉黑和删除语义清晰 |
| 好友来源 | 分享卡片 | 通讯录导入 | 微信根本不开放关系链 |
| streak | 客户端算，服务端存 | 服务端链式计算 | 离线也要能正确显示 |
| 排行缓存 | 不建缓存表 | 每日定时任务生成 | 20 人规模实时算更快，少一层不一致 |
| 补卡 | 不支持 | 支持补卡 | 无学习价值，易刷指标 |

## 8. 成本与落地路径

| 阶段 | 内容 | 成本 |
|---|---|---|
| P0 | 只做本地快照聚合 + 自己的历史曲线，不联机 | ¥0，零风险 |
| P1 | 接云开发，做"圈子 + 完成状态榜"（无好友） | ¥19.9/月 |
| P2 | 加好友系统与详情页 | 同上 |
| P3 | 加名次模式、点赞鼓励 | 同上 |

**强烈建议按 P0 → P1 走**。P0 完全不碰后端，能先验证"用户是否真的想看自己的连续天数曲线"，
这个需求成立再投入云端。如果 P0 没人用，P1 的圈子和好友也不会有人用。
